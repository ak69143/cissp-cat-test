フレームワーク早見表

NIST・ISO・セキュリティモデル・コンプライアンス規格を一覧で整理。
試験では「どのフレームワークがどの目的か」を問われる。

NIST CSF 2.0
NISTフレームワーク
サイバーセキュリティフレームワーク
サイバーセキュリティリスク管理の共通言語。2024年v2.0で「統治 Govern」が追加。
6つのコア機能（2024年v2.0）
  • Govern（統治）：v2.0で追加。組織の優先事項・リスク許容度を定義
  • Identify（特定）：資産・リスクの識別
  • Protect（防御）：適切な保護策の実施
  • Detect（検知）：セキュリティイベントの検出
  • Respond（対応）：インシデント対応活動
  • Recover（回復）：能力・サービスの復旧
▶ CISSP 出題ポイント
v2.0でGovernが追加されたことを必ず覚える。「組織のリスク管理体制の構築」はGovern。強制力なし（任意のフレームワーク）。
NIST RMF (SP 800-37 Rev.2)
NISTフレームワーク
リスク管理フレームワーク
連邦政府システム向けのリスク管理プロセス。7ステップで構成。
7ステップ（Rev.2でPrepareが追加）
  • Prepare：リスク管理の準備・前提整備（Rev.2で追加）
  • Categorize：システムと情報の分類（FIPS 199準拠）
  • Select：セキュリティコントロールの選択
  • Implement：コントロールの実装
  • Assess：コントロールの評価
  • Authorize：運用承認（ATO: Authority to Operate）
  • Monitor：継続的な監視
▶ CISSP 出題ポイント
ステップ順序を覚える。Authorizeステップでシステムの運用が承認される。Rev.2でPrepareが先頭に追加された点も問われる。
NIST SP 800-53 Rev.5
NISTフレームワーク
セキュリティとプライバシーコントロール
連邦政府情報システム向けのセキュリティコントロールカタログ。20のコントロールファミリー。
主なコントロールファミリー（20種）
  • AC（Access Control）、AT（Awareness Training）
  • AU（Audit and Accountability）、CA（Assessment）
  • CM（Configuration Management）、CP（Contingency Planning）
  • IA（Identification and Authentication）、IR（Incident Response）
  • Rev.5でプライバシーコントロール（PT, RA等）を統合
▶ CISSP 出題ポイント
RMFのSelectステップで参照するカタログ。Rev.5でプライバシーを統合。コントロールはBaseline（Low/Moderate/High）に分類される。
NIST SP 800-171
NISTフレームワーク
CUI保護（非連邦システム向け）
連邦政府以外のシステムでCUI（管理対象未分類情報）を扱う場合の要件。
概要
  • SP 800-53のサブセット（110のセキュリティ要件）
  • 14のファミリーで構成
  • 防衛調達（DFARS）で準拠が義務化
  • CMMC（Cybersecurity Maturity Model Certification）の基礎
▶ CISSP 出題ポイント
「政府の請負業者がCUIを扱う場合の要件」= SP 800-171。SP 800-53との違いは連邦機関か否か。
ISO/IEC 27001
ISO規格
ISMS要件規格（認証規格）
情報セキュリティマネジメントシステム（ISMS）の要件を定める国際認証規格。
構成
  • Annex A：93のセキュリティコントロール（2022年版）
  • PDCAサイクルに基づくマネジメントシステム
  • 第三者認証が可能（27002との違い）
  • スコープ定義・リスクアセスメント・SoA（適用宣言書）が必須
▶ CISSP 出題ポイント
「認証取得できる」のは27001のみ。27002はガイダンスで認証なし。SoA（Statement of Applicability）でコントロールの適用可否を宣言する。
ISO/IEC 27002
ISO規格
セキュリティコントロール実装ガイダンス
27001のAnnex Aコントロールの実装手引き。認証規格ではなくガイダンス。
2022年版の4テーマ分類
  • 組織的コントロール（37項目）
  • 人的コントロール（8項目）
  • 物理的コントロール（14項目）
  • 技術的コントロール（34項目）
  • 合計93コントロール（旧版114から統合整理）
▶ CISSP 出題ポイント
27001の「要件（MUST）」に対し、27002は「推奨（SHOULD）」。認証は27001、実装ガイドは27002と覚える。
ISO/IEC 27005
ISO規格
情報セキュリティリスク管理
ISMSにおけるリスク管理プロセスのガイダンス。ISO 31000をベースに情報セキュリティ特化。
プロセス
  • コンテキスト確立 → リスク特定 → リスク分析
  • リスク評価 → リスク対応 → 残留リスク受容
  • リスクコミュニケーション・モニタリング
  • 定量・定性どちらのアプローチも許容
▶ CISSP 出題ポイント
「ISMSのリスク管理方法論」= 27005。リスク対応の4択（回避・軽減・移転・受容）はここで定義。
ISO/IEC 27701
ISO規格
プライバシー情報マネジメント（PIMS）
27001/27002をプライバシー（PII保護）に拡張した規格。GDPRへの対応を支援。
概要
  • 27001の拡張規格（27001取得が前提）
  • PII管理者（Controller）とPII処理者（Processor）の要件を規定
  • GDPR, CCPA等のプライバシー規制へのマッピング提供
▶ CISSP 出題ポイント
「プライバシー + ISMS = 27701」。GDPRのDPIA（データ保護影響評価）実施にも活用される。
ISO 31000
ISO規格
リスク管理（汎用）
あらゆる種類のリスクに適用できる汎用リスク管理フレームワーク。
概要
  • 原則・フレームワーク・プロセスの3要素で構成
  • 業種・規模を問わず適用可能
  • 27005はこれを情報セキュリティに特化させたもの
▶ CISSP 出題ポイント
「情報セキュリティのリスク管理」=27005、「組織全体のリスク管理」=31000と区別する。
Bell-LaPadula
セキュリティモデル
機密性モデル
「機密情報の漏洩防止」に特化したMACモデル。軍の機密区分を基に設計。
2つの特性
  • Simple Security Property（ss特性）：「No Read Up」
    被験者は自分の機密区分より高いオブジェクトを読めない
  • Star Property（*特性）：「No Write Down」
    被験者は自分の機密区分より低いオブジェクトに書けない
  • 「上を読むな、下に書くな」＝機密情報の下方漏洩を防ぐ
▶ CISSP 出題ポイント
機密性（Confidentiality）のみを保護。完全性は扱わない。「政府・軍の機密システム」に適した場面で選ぶ。Bibaとセットで覚える。
Biba
セキュリティモデル
完全性モデル
Bell-LaPadulaの「逆」。データの完全性（汚染防止）に特化。
2つの特性（BLPの逆）
  • Simple Integrity Property：「No Read Down」
    被験者は自分より完全性が低いオブジェクトを読めない（汚染防止）
  • Star Integrity Property（*特性）：「No Write Up」
    被験者は自分より完全性が高いオブジェクトに書けない
  • 「下を読むな、上に書くな」＝低品質データによる汚染を防ぐ
▶ CISSP 出題ポイント
完全性（Integrity）のみを保護。BLPとBibaは方向が逆。「データの完全性保証」「金融システム」のシナリオで選ぶ。
Clark-Wilson
セキュリティモデル
商用完全性モデル
商用システム向けの完全性モデル。職務分離と承認済み手順によりデータ完全性を保証。
4つの要素
  • CDI（Constrained Data Items）：保護対象データ
  • UDI（Unconstrained Data Items）：非保護データ（入力等）
  • TP（Transformation Procedures）：CDIを操作する承認済みプロシージャ
  • IVP（Integrity Verification Procedures）：CDIの整合性検証
  • アクセス三重構造：主体 → TP → CDI
▶ CISSP 出題ポイント
Bibaが「格付けレベル」で制御するのに対し、Clark-Wilsonは「承認された手順（TP）を通じてのみ」データを操作できる。職務分離・監査を組み込む。
Brewer-Nash（Chinese Wall）
セキュリティモデル
利益相反防止モデル
コンサルティング・金融業向け。過去のアクセス履歴に基づいて利益相反を動的に制御。
仕組み
  • オブジェクトを「競合利益クラス」にグループ化
  • 一度A社のデータにアクセスしたら、競合B社データへのアクセスを自動禁止
  • 時間経過でアクセス可能オブジェクトが変化する動的モデル
▶ CISSP 出題ポイント
「利益相反（Conflict of Interest）」の防止 = Brewer-Nash。動的に変化するアクセス制御が特徴。コンサルや投資銀行のシナリオで登場。
Take-Grant
セキュリティモデル
アクセス権伝播モデル
グラフ理論でアクセス権の伝播を形式的に分析するモデル。
4つの操作
  • Take：別の主体からアクセス権を取得
  • Grant：別の主体へアクセス権を付与
  • Create：新しい主体・客体を作成
  • Remove：アクセス権を削除
▶ CISSP 出題ポイント
「アクセス権の伝播を分析するモデル」= Take-Grant。「誰が誰に権限を渡せるか」の形式的証明に使う。試験では名称と目的の照合が多い。
Graham-Denning
セキュリティモデル
保護権限管理モデル
主体・客体の作成・削除と権限の移譲を定義する8つの保護権限を規定。
8つの保護権（抜粋）
  • 主体の作成・削除、客体の作成・削除
  • アクセス権の読み取り・付与・削除・移転
▶ CISSP 出題ポイント
「8つの保護権限」が特徴。Take-Grantより詳細。試験では名称と「主体/客体の生成・削除」を管理するモデルとして問われる。
Harrison-Ruzzo-Ullman (HRU)
セキュリティモデル
アクセス行列モデル
主体×客体のアクセス行列でシステムの安全性（Safety）を形式的に検証。
概要
  • アクセス行列（Access Matrix）で権限状態を表現
  • 操作（コマンド）による状態遷移を定義
  • 「この権限が漏れることはないか？」を証明するための理論モデル
▶ CISSP 出題ポイント
「アクセス行列で安全性を証明」= HRU。完全な安全性証明は一般的には決定不能（undecidable）であることが知られている。
Trusted Computing Base (TCB)
セキュリティモデル
信頼できるコンピューティング基盤
セキュリティポリシーを強制するすべてのH/W・S/W・ファームウェアの集合。
概要
  • TCBに含まれるもの：OS・ハイパーバイザー・セキュリティ機能
  • TCBが小さいほど攻撃面が小さく、検証が容易
  • 参照モニター（Reference Monitor）はTCBの中核概念
▶ CISSP 出題ポイント
「TCBは小さいほど良い」が基本原則。参照モニターの3条件：常に呼び出される・改ざん不可・検証可能な小ささ。
Lattice-Based Access Control
セキュリティモデル
格子ベースアクセス制御
セキュリティラベルを格子（半順序集合）として定義し、情報フローを制御。MACの数学的基礎。
概要
  • 各主体・客体にセキュリティレベルを割り当て
  • 情報フローは低 → 高方向のみ許可（機密性）
  • Bell-LaPadula・Bibaはこの格子構造を利用
▶ CISSP 出題ポイント
MACモデルの数学的基盤。「情報フロー制御」の文脈で登場。BLPやBibaの理論的土台として理解する。
State Machine Model
セキュリティモデル
状態機械モデル
システムを状態の集合とその遷移として表現。すべての状態がセキュアであることを保証。
概要
  • 初期状態がセキュアであること
  • セキュアな状態からセキュアな状態へのみ遷移
  • Bell-LaPadula・Bibaはこのモデルを基礎にする
▶ CISSP 出題ポイント
「状態機械モデル」= セキュリティモデルの基礎理論。BLPやBibaが「どの状態でもセキュリティ特性を満たす」ことをこのモデルで証明する。
Non-Interference Model
セキュリティモデル
非干渉モデル
高機密レベルの操作が低機密レベルの出力に影響を与えないことを保証。サイドチャネル攻撃対策の理論基盤。
概要
  • 情報フローの隠れたチャネル（コバートチャネル）防止
  • 高セキュリティドメインの処理が低セキュリティドメインに「干渉しない」
  • BLPより厳格（タイミング攻撃等も考慮）
▶ CISSP 出題ポイント
「コバートチャネル（隠れチャネル）」の防止モデル。情報の意図しない漏洩経路を理論的に排除したい場合のモデル。
COBIT 2019
ガバナンス
ITガバナンスフレームワーク
ITガバナンスとマネジメントを包括的に定義。ISACA発行。企業のIT統治に広く使われる。
概要
  • 6つのガバナンス原則（COBIT 2019）
  • 40の目標（旧37）でITプロセスを体系化
  • ISO 38500（IT統治）との整合性
  • VAL IT（価値管理）・Risk IT（リスク管理）を統合
▶ CISSP 出題ポイント
「ITガバナンス」= COBIT。ITIL（IT運用/サービス管理）と混同しない。経営層がITを統治するためのフレームワーク。
ITIL 4
ガバナンス
ITサービス管理フレームワーク
ITサービスのライフサイクル管理のベストプラクティス集。COBITとは補完関係。
ITIL 4のコア概念
  • 4つのディメンション（組織・情報/技術・パートナー・バリューストリーム）
  • SVS（サービスバリューシステム）
  • 34のプラクティス（旧26プロセス）
  • 継続的改善（Continual Improvement）を重視
▶ CISSP 出題ポイント
COBIT=ガバナンス、ITIL=サービス管理（運用）と区別する。「変更管理（Change Management）」「インシデント管理」のベストプラクティスとして登場。
SABSA
ガバナンス
セキュリティアーキテクチャフレームワーク
ビジネス要件からセキュリティアーキテクチャを導出するリスクベースフレームワーク。
6つのアーキテクチャ層（Zachmanに対応）
  • Contextual（コンテキスト）→ Conceptual → Logical
  • Physical → Component → Operational
  • 各層で「資産・動機・プロセス・人・場所・時間」の6次元
▶ CISSP 出題ポイント
「エンタープライズセキュリティアーキテクチャ」= SABSA。ビジネス属性（Business Attributes）からセキュリティ要件を導出する点が特徴。TOGAFとの違いも問われる。
COSO
ガバナンス
内部統制フレームワーク
財務報告の信頼性を確保するための内部統制フレームワーク。SOX法の基礎。
5つのコンポーネント
  • 統制環境・リスク評価・統制活動
  • 情報とコミュニケーション・モニタリング
  • 3つの目的：業務の有効性・財務報告の信頼性・コンプライアンス
▶ CISSP 出題ポイント
「財務報告の内部統制」= COSO。SOX法対応に使われる。セキュリティ試験では「どのフレームワークが財務統制向けか」という問いで登場。
PCI DSS v4.0
コンプライアンス
カード決済セキュリティ基準
クレジットカード情報を扱う組織が準拠必須の業界基準。VISA/Mastercard等が策定。
12要件（6目標）
  • 安全なネットワーク構築・維持（要件1-2）
  • カード会員データの保護（要件3-4）
  • 脆弱性管理プログラム（要件5-6）
  • 強固なアクセス制御（要件7-9）
  • ネットワーク監視・テスト（要件10-11）
  • 情報セキュリティポリシー（要件12）
▶ CISSP 出題ポイント
「12要件」が頻出。カード情報（PAN）は保存不可が原則。v4.0では認証強化とカスタマイズドアプローチが追加された。
GDPR
コンプライアンス
EU一般データ保護規則
EU市民の個人データを保護する規制。EU域外の組織にも適用される。2018年施行。
主要原則（7原則）
  • 適法性・公正性・透明性 / 目的の限定 / データ最小化
  • 正確性 / 保存の制限 / 完全性と機密性 / 説明責任
  • 個人の権利：忘れられる権利・アクセス権・ポータビリティ権
  • データ侵害通知：DPA（監督機関）へ72時間以内に通知
▶ CISSP 出題ポイント
72時間通知・忘れられる権利（消去権）・DPO（データ保護責任者）の選任義務を覚える。「域外適用」（EU市民データを扱えば非EU企業にも適用）も頻出。
HIPAA
コンプライアンス
米国医療情報保護法
医療情報（PHI）の保護を義務付ける米国法律。医療機関・保険会社・取引先に適用。
3つのルール
  • Privacy Rule：PHIの使用・開示を制限
  • Security Rule：電子PHI（ePHI）のセキュリティ要件（管理・物理・技術的保護措置）
  • Breach Notification Rule：侵害発生時の通知義務（60日以内）
  • Business Associate（BAA契約）：PHIを扱う取引先にも適用
▶ CISSP 出題ポイント
「医療情報」= HIPAA。PHIとePHIの区別・BAA（Business Associate Agreement）の締結義務・60日通知を覚える。
SOC 2
コンプライアンス
サービス組織のセキュリティ報告
クラウド・SaaSプロバイダー向けの第三者保証報告書。AICPA（米国公認会計士協会）が策定。
5つのトラストサービス基準（TSC）
  • Security（必須）：不正アクセスからの保護
  • Availability：合意したパフォーマンスを維持
  • Confidentiality：機密情報の保護
  • Processing Integrity：処理の完全性
  • Privacy：個人情報の収集・使用・保持
  • Type I（時点評価）vs Type II（期間評価）
▶ CISSP 出題ポイント
「クラウドプロバイダーへのセキュリティ要求」= SOC 2。Type II（6ヶ月以上の運用実績）が実質的に信頼性の証明。Securityのみ必須で他は任意。
