#07リスク管理
リスク対応の4択を使い分ける
軽減・移転・受容・回避 ── コストと影響度で判断する
リスクの完全排除は不可能です。コスト対効果を考えて対応方法を選びます。
· 軽減（Mitigate）: 対策してリスクを下げる
· 移転（Transfer）: 保険・外部委託でリスクを移す
· 受容（Accept）: 低リスクなら許容する
· 回避（Avoid）: その活動自体をやめる
選び方の目安
小確率・低損害 → 受容／大損害・対策コスト過大 → 移転（保険）
高損害・高発生率 → 軽減／リスクが許容できない → 回避
リスクマネジメント意思決定
#08リスク管理
CIA の重み：機密性が最重要
セキュリティ問題では、機密性の侵害が最も深刻とされることが多い
CIA（機密性・完全性・可用性）は等価ではありません。データ漏えいは取り返しがつかないため、機密性を最優先に考えます。可用性の問題（ダウンタイム）は回復できますが、漏えいたデータは戻りません。
例題の考え方

✗ サーバーダウン → 可用性問題（回復可能）
✓ 顧客データ漏えい → 機密性侵害（取り戻せない）

#12リスク管理
Due Diligence と Due Care の区別
Due Diligence = 調査・評価する責任 ／ Due Care = 適切に実施する責任
· Due Diligence（デュー・ディリジェンス）: 意思決定前に適切な調査・評価を行うこと

両方を果たすことで「合理的な注意義務」を果たしたと言えます。

#26暗号・技術
対称 vs 非対称暗号の使い分け
対称 = 高速・大量データ向け ／ 非対称 = 鍵配送・デジタル署名向け
· 対称暗号（AES等）: 同じ鍵で暗号化・復号。高速だが鍵の安全な共有が課題
· 非対称暗号（RSA等）: 公開鍵・秘密鍵のペア。遅いが鍵配送問題を解決
実際のTLSはハイブリッド方式（非対称で鍵交換→対称で通信暗号化）を採用。
例題の考え方

#27暗号・技術
ハッシュ = 完全性の確認
ハッシュは一方向関数。暗号化ではなく、データ改ざんの検出に使う
ハッシュ（SHA-256等）は復号できません。暗号化との混同が最も多い誤解です。同じ入力からは常に同じハッシュ値が得られるため、改ざん検出に使われます。
例題の考え方
Q: ハッシュ値が一致した → 何が保証される？
✗ データが暗号化されている
✓ データが改ざんされていない（完全性の確認）

ポリシーは定期的に見直す
セキュリティポリシーは一度作ったら終わりではなく、定期的にレビューする
技術・脅威・ビジネス環境は常に変化します。古いポリシーは有名無実化し、コンプライアンス違反や実態との乖離を生みます。年1回以上のレビューがベストプラクティスです。
例題の考え方
3年前に作ったパスワードポリシーがまだ運用されている
✗ 問題ない。一度作ったポリシーは変えなくていい
✓ 定期的にレビューし、現在の脅威環境に合わせて更新する

#34マネージャー思考
セキュリティとプライバシーはセットで考える
個人データを守るセキュリティと、その利用の透明性（プライバシー）は別物
セキュリティが強固でも、過剰収集・目的外利用はプライバシー侵害です。GDPRなどでは「データ最小化の原則」があります。セキュリティとプライバシーの両立が必要です。
例題の考え方
セキュリティ監視のために全従業員の行動ログを詳細に記録する
✓ セキュリティ的には有効だが、プライバシーポリシー・法令への準拠も必要

#37インシデント対応
インシデント対応の正しい順序
検知 → 封じ込め → 根絶 → 復旧 → 事後分析
順序を守ることが重要です。封じ込めを飛ばして復旧しようとするのが最も多い間違いです。復旧の前に必ず「封じ込め（被害拡大防止）」と「根絶（原因除去）」を行います。
例題の考え方
Q: ランサムウェア感染を確認した。最初にすべきことは？
✗ バックアップからシステムを復旧する → 復旧（早すぎる）
✓ 感染端末をネットワークから切断する → 封じ込め

#38インシデント対応
フォレンジックは証拠保全が最優先
インシデント調査では、まず証拠を保全してから分析・復旧を行う
証拠の改ざん・消失を防ぐことが最優先です。揮発性の高い情報（メモリ・一時ファイル等）から先に収集します。シャットダウンするとメモリ上の証拠が消えます。
揮発性の順序（高→低）
メモリ（RAM）→ スワップ・一時ファイル → ネットワーク接続状態 → ディスク → バックアップ
デジタルフォレンジック証拠保全Chain of Custody
#39インシデント対応
BCP と DR の違い
BCP = 事業継続計画（事業全体）／ DR = 災害復旧計画（ITシステム）
· BCP（Business Continuity Plan）: 災害・障害時に事業を継続するための包括的な計画。ビジネス全体を対象とする
· DR（Disaster Recovery）: ITシステム・インフラの復旧計画。BCPの一部
DR は BCP のサブセットです。
例題の考え方
工場が使えない時の代替生産計画 → BCP（ビジネス継続）
サーバーをバックアップから復旧する → DR（システム復旧）
BCPDR事業継続
#40インシデント対応
RTO と RPO の定義と優先順位
RTO = 復旧目標時間（どのくらいで戻すか）／ RPO = 復旧目標時点（どこまで戻るか）
· RTO（Recovery Time Objective）: 障害発生から復旧までの目標時間。短いほどコストが高い
· RPO（Recovery Point Objective）: 許容できるデータ損失の時間的範囲。短いほど頻繁なバックアップが必要
どちらもビジネスニーズとコストのバランスで決める。
例題の考え方
RTO 4時間 → 障害から4時間以内にシステム復旧
RPO 1時間 → 最大1時間分のデータ損失まで許容
