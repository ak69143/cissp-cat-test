#01 優先順位
予防 ＞ 検知 ＞ 対応
コントロールを選ぶときは「予防的」を最優先に選ぶ
CISSPは「問題が起きる前に防ぐ」ことを最も重視します。
検知（発見）や対応（修復）は後手の対策。予防が最善です。

Q: 不正アクセスへの最善の対策は？
✗ 侵入検知システム（IDS）を導入する → 検知（後手）
✓ ファイアウォールでアクセスを制限する → 予防

#02 優先順位
「最初にすべきこと」＝ 確認・承認
即座に動く前に、必ずスコープ確認・上位への報告・承認取得を行う
CISSPは衝動的な対応より、適切なプロセスを重視します。
何かが起きたとき、最初の行動は「把握する」「報告する」です。勝手に修復しない。

✗ すぐにシステムをシャットダウンする
✓ インシデントの範囲を把握し、経営層に報告する

#03 リスク管理
リスク対応の4択を使い分ける
軽減・移転・受容・回避 ── コストと影響度で判断する
リスクの完全排除は不可能です。コスト対効果を考えて対応方法を選びます。
· 軽減（Mitigate）: 対策してリスクを下げる
· 移転（Transfer）: 保険・外部委託でリスクを移す
· 受容（Accept）: 低リスクなら許容する
· 回避（Avoid）: その活動自体をやめる
例題の考え方
小さな確率の低損害リスク → 受容
大損害だが対策コスト過大 → 移転（保険）
高損害・高発生率 → 軽減

#04 リスク管理
CIA の重み：機密性が最重要
セキュリティ問題では、機密性の侵害が最も深刻とされることが多い
CIA（機密性・完全性・可用性）は等価ではありません。
データ漏えいは取り返しがつかないため、機密性の保護を最優先に考えます。
可用性の問題（ダウンタイム）は一時的に回復できますが、漏えいたデータは戻りません。
例題の考え方
Q: サーバーダウン vs 顧客データ漏えい、どちらが深刻？
✗ サーバーダウン → 可用性問題（回復可能）
✓ 顧客データ漏えい → 機密性侵害（取り戻せない）
CIA トライアド 資産保護
#05 コントロール
管理的 ＞ 技術的 ＞ 物理的
ポリシー・手順（管理的コントロール）を最初に検討する
技術的コントロールは、管理的コントロールを実装するための手段に過ぎません。
まずポリシーや手順を整備し、それを技術や物理で実現します。
「ツールを入れる前にルールを作る」がCISSPの考え方です。
例題の考え方
Q: 強いパスワードを強制するには？
✗ システムで文字数を強制する → 技術的（先走り）
✓ パスワードポリシーを策定する → 管理的（先に来る）

#06 アクセス制御
最小権限（Least Privilege）
業務に必要な最低限の権限のみを付与する
権限を絞ることで、アカウント侵害時の被害範囲を最小化できます。
「とりあえず広い権限を与えておく」はCISSP的に完全にNG。
Need-to-know（知る必要がある情報のみアクセス可）とセットで考えます。
例題の考え方
✗ 全員に管理者権限を付与する（便利だから）
✓ 業務に必要な権限のみを個別に付与する
IAM Need-to-Know 権限管理
#07 アクセス制御
職務分離（Separation of Duties）
単一人物が不正を完結できる権限を持たせない
一人の人間が「申請 → 承認 → 実行」をすべてできる状態は危険です。
職務を分けることで、内部不正や意図しない誤りを防止します。
2人の協力なしに不正が成立しない設計が理想です。
例題の考え方
✗ 経理担当が支払い申請も承認も実行もできる
✓ 申請者と承認者を別の人物にする
内部統制 不正防止
#08 コントロール
デフォルト拒否（Default Deny）
明示的に許可されていないものはすべて拒否する
「許可リスト（Allowlist）方式」とも呼ばれます。
何も指定しなければ拒否が正しいデフォルト状態です。
「とりあえず許可しておく」は攻撃者に隙を与えます。
例題の考え方
✗ ファイアウォール：全通信を許可し、危険なものだけブロック
✓ ファイアウォール：全通信を拒否し、必要なものだけ許可
ファイアウォール アクセス制御 セキュリティ設計
#09 マネージャー思考
技術者ではなくCISOとして考える
「技術的に正しい」より「ビジネスリスクとして適切か」を問う
CISSPは技術試験ではなくセキュリティマネジメントの試験です。
エンジニアが選ぶ答えより、リスク・コスト・ビジネスへの影響を考えた答えが正解になります。
「まず技術で解決」ではなく「まずリスク評価・承認プロセス」を選びましょう。
例題の考え方
Q: 重大な脆弱性を発見した。最善の対応は？
✗ すぐにパッチを適用する → エンジニア的思考
✓ リスクを評価し、変更管理プロセスに従って承認を得てから適用
ガバナンス 変更管理 リスク評価
#10 インシデント対応
インシデント対応の正しい順序
検知 → 封じ込め → 根絶 → 復旧 → 事後分析
インシデント対応には決まった手順があります。順序を守ることが重要です。
特に間違えやすいのが「封じ込めを飛ばして復旧しようとする」パターン。
復旧の前に必ず封じ込め（被害の拡大防止）と根絶（原因除去）を行います。
例題の考え方
Q: ランサムウェア感染を確認した。最初にすべきことは？
✗ バックアップからシステムを復旧する → 復旧（早すぎる）
✓ 感染端末をネットワークから切断する → 封じ込め
